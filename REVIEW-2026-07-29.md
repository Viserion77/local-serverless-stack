## 1. Executive summary

I brought the real stack up (the `self-hosted` example, self engine, no Docker), drove the pipeline
end to end, ran two instances in parallel and built a synthetic project of **40 services × 400
lambdas × 400 tables** to measure the scenario that motivates the project.

**The product works.** The `POST /orders → DynamoDB → SQS → Lambda → S3 + EventBridge → rule →
Lambda → DynamoDB` pipeline runs end to end in ~120 ms, DLQ redrive honours `maxReceiveCount`,
OpenSearch answers search and aggregation, persistence survives a restart, and two parallel
instances stay completely isolated. Boot in 2 s, 40 services registered in 0.9 s (22 ms each), API
latency under 200 ms with 400 tables.

**But there were four problems that hit your use case exactly**, all now fixed:

| # | Problem | Effect on the 40-service monorepo |
|---|---|---|
| 1 | A Node worker forked **eagerly** per registered service | **2.0 GB of idle RAM** before any handler runs |
| 2 | `ListTables` without pagination (AWS cuts off at 100) | Of your **400 tables, only 100 showed up** in the dashboard and the API |
| 3 | Explorers with a hardcoded `us-east-1` default region | A project outside us-east-1 → **the API returned empty lists** (the dashboard escaped it; the CLI/`LssClient`/curl did not) |

## 3. Changes applied

Grouped by theme. Every one has a test and a comment explaining the *why*, in the codebase's style.

### 3.1 Scale — on-demand workers (the highest-impact change)

**`src/server/services/lambda-runtime-manager.ts`, `config-manager.ts`, `routes/{lambdas,services}.ts`**

`syncService()` forked the worker at registration time. It now resolves where the handlers live (so
a broken artifact **still fails at registration**, not on the first call) and leaves the fork to the
first `invoke`.

- `lambdaRuntime.lazy` — **default `true`**. `false` restores the old behaviour.
- `lambdaRuntime.idleTimeoutMs` — **default `60000`** (1 min). Unloads a worker that went quiet;
  never interrupts an in-flight invocation. `0` keeps it alive forever.
- `lambdaRuntime.maxWarmWorkers` — **default: 1 per GB of RAM, clamped to 2..12**. A hard ceiling on
  resident workers; on overflow it unloads the least recently invoked one. This is what guarantees
  the host's memory depends on the services **in use**, not the services **registered** — a burst
  that touches all 40 within the idle window still settles at the ceiling.

Measured on the synthetic 40-service stack, with `maxWarmWorkers: 4` and `idleTimeoutMs: 8000`:

| moment | workers | RSS |
|---|---|---|
| 40 registered, nothing invoked | 0 | **128 MB** |
| right after invoking **all 40** in a burst | **4** (the ceiling) | 329 MB |
| 11 s later, idle | **0** | **132 MB** |
| the next request | re-fork | 200 in **23 ms** |

- A new internal `idle` status, but `getRuntimeInfo()` reports `online` + `warm: false` — no
  consumer (UI, routes, dispatch) had to change, because for all of them "idle" means "it will
  answer". `GET /api/lambdas` exposes `warm`, `GET /api/services` exposes `runtimeWarm`.

### 3.2 Scale — WAL, watchers and pagination

- **`src/server/engine/store/wal.ts`** — compaction only happened through `dehydrate()`, which is
  triggered by the idle sweep and by the LRU. A continuously written table never goes idle: the WAL
  grew for the whole session and was fully re-read on the next boot. The table now compacts itself
  when the WAL passes 4 MB **and** twice the resident size.
- **`src/server/services/source-watcher.ts`** — `fs.watch(root, {recursive:true})` registers one
  inotify watch per directory in the tree. Measured on the example: **1,756 directories, of which 4
  hold code**. With 40 services that would be ~70 thousand watches (`max_user_watches` is usually
  8,192 on a dev machine). `IGNORED_SEGMENTS` only filtered the events, never the watches. Now: a
  non-recursive watch on the root plus one recursive watch per non-ignored subdirectory.
- **Pagination** in `dynamo-explorer.ts`, `seed-manager.ts`, `resource-provisioner.ts`
  (`ListTables`, cut off at 100) and `queue-inspector.ts` + `resource-provisioner.ts`
  (`ListQueues`, cut off at 1000). The engine implements the cut-off faithfully to AWS — the bug was
  on the consumer side.

### 3.3 Region fix in the explorers

**`src/server/services/explorer-region.ts` (new)** + the `dynamo-explorer`, `secrets-explorer` and
`opensearch-explorer` constructors.

`DynamoExplorer`, `SecretsExplorer` and `OpenSearchExplorer` had a hardcoded
`defaultRegion = 'us-east-1'`, and `setDefaultRegion()` was never called at boot (only `SeedManager`
called it). `S3Explorer`/`QueueInspector` already read the engine's region in their constructor —
the inconsistency hid the bug. The dashboard always sends `?region=` (read from `/api/config`), so
it only broke for the **CLI, `LssClient` and curl**. Now: the constructor reads the configured
region, `index.ts` pins it explicitly at boot, and `PUT /api/config` / `POST /api/config/reload`
re-apply it.

The symptom before the fix, on the shipped example (region `us-west-2`):

```
$ curl .../api/dynamo/tables        → {"tables":[]}
$ curl .../api/dynamo/tables?region=us-west-2  → 2 tables
```

### 3.4 `persistence: false` now means what it promises

**`src/server/engine/store/memory-store.ts` (new)**, `engine-store.ts`, `self-backend.ts`.

`config.persistence` was only consulted for the SQS message snapshot. Catalogues and the WAL were
always written — tables and queues survived a restart and every run left `.lss/engine/` behind. Now
`persistence: false` swaps the store for an in-memory one: nothing is created on disk, and no boot
inherits state.

Verified: with `persistence:false`, `.lss/` contains only `orchestrator.{log,pid}`, and
`/api/resources` comes back empty after a restart.

### 3.5 Isolation between projects and instances

- **`src/server/services/project-scope.ts` (new)** — `projectCacheSegment()` moved out of
  `cache-manager.ts` (re-exported from there, so importers are unaffected) so it can be used without
  an import cycle.
- **`config-manager.ts`** — a new env var, **`LSS_ENGINE_DATA_DIR`**: with it, plus
  `LSS_DASHBOARD_PORT` and `LSS_ENGINE_PORT`, a second instance boots without writing any config
  file and without sharing anything with the dev stack:
  ```bash
  LSS_DASHBOARD_PORT=3250 LSS_ENGINE_PORT=14766 \
    LSS_ENGINE_DATA_DIR=/tmp/lss-run-7/engine npx lss start --self-engine
  ```
  Validated: the engine's state went entirely to the env's directory and `.lss/` was left with only
  `orchestrator.{log,pid}`.
- **`config-manager.ts`** — without `stateDir`, the engine's and the aoss sidecar's `dataDir` fell
  back to `~/.lss/engine` and `~/.lss/aoss`, which are **global**: every project on the machine
  shared one set of tables. Now: `~/.lss/projects/<slug>-<hash>/{engine,aoss}`.
- **`lambda-runtime-manager.ts`** — the artifact extraction directory was
  `~/.lss/orchestrator/runtime/<serviceName>/<hash>`, with no project scope, and a new registration
  `rm -rf`s the base directory. Two checkouts with a service called `api` → the second one deleted
  the code the first one's worker was running. Now scoped per project.
- **`bin/cli.js`** — `lss start` with `engine: "self"` no longer exports any `LSS_LOCALSTACK_*` or
  `LOCALSTACK_AUTH_TOKEN`. Beyond the leak (the env is inherited by every forked worker), each
  exported key was reported by `GET /api/config` as `envOverridden` — which **greyed out 7 fields in
  the Settings tab** for values you never set.

### 3.6 Errors that took the process down

- **`src/server/index.ts`** — `app.listen()` with no `error` handler: an `EADDRINUSE` on the
  dashboard's port became an unhandled exception **after** the engine had already bound its own port
  and armed the delivery loops, leaving a half-alive process. Now: a named message + a clean
  shutdown with exit code 1.
- **`src/server/dev/dynamo-proxy.ts`** — same problem; since the proxy is optional, it degrades to a
  warning and the orchestrator stays up.

### 3.7 Testability

- **`src/client/{http,namespaces/queues}.ts`** — the server's `awaitIdle` default (15,000 ms) was
  **equal** to `LssClient`'s default HTTP timeout (15,000 ms): the product's main waiting primitive
  resolved or threw depending on scheduling. The `awaitIdle` request now has its own budget (the
  server's `timeoutMs` plus 5 s of slack).
- **`src/server/index.ts`** — any `/api/*` that no router claimed now answers a **JSON 404**, not
  the SPA's `200 text/html`. Before, a wrong path read as a success to curl, to `LssClient` and to
  any test asserting on the response.
- **`tests/unit/engine/dispatch/helpers.ts`** — the root cause of the `ENOTEMPTY` flake documented
  in AGENTS.md: `cleanup()` did an `rm -rf` without `flushAll()`, racing the catalogue's debounced
  (20 ms) writes. It now drains first and has a short retry. I confirmed the flake is **CPU
  contention**: it reappeared while the 40-worker instance was running and vanished afterwards — 5
  clean runs in a row.

### 3.8 A dashboard with no "LocalStack" in self mode

**`src/ui/src/services/engine.ts` (new)** + `App.vue`, `OverviewPage.vue`, `QueuesView.vue`,
`BucketsView.vue`, `ServicesList.vue`, `ServiceDetailPage.vue`, `api.ts`.

The header badge always said "LocalStack: Running"; the Overview said "One LocalStack. Every
microservice." and showed `endpoint: :4566` / `image: localstack/localstack:latest` / `mode:
managed` **even with the self engine on :14666** — the field a developer copies into the SDK pointed
at a dead port. Empty states and delete confirmations said "in LocalStack".

Everything now reads `engineLabel`/`isSelfEngine`, fed by `/api/health` (`engine.kind`) and
`/api/config`. On the server, `GET /api/health` gained `engineRunning`; `localstack` remains as a
deprecated alias.

### 3.9 Documentation

`README.md`, `docs/FEATURES.md`, `docs/SELF_ENGINE.md` and `docs/CONFIGURATION.md` updated for all
of the above (AGENTS.md §4's requirement).

## 4. Decisions I made — and the alternatives

You asked me to choose and to list the alternatives.

### 4.1 `lambdaRuntime.lazy` defaulting to **true**

- **I chose:** on by default. It is the difference between 2.0 GB and 128 MB in your scenario, and
  the measured cost is 23 ms on each service's first call.
- **Alternatives:** (a) default `false` and opt in — more conservative, but nobody turns on what
  they do not know exists, and the product's target scenario is precisely the one that suffers;
  (b) a multi-tenant worker (N services per process) — saves more, but breaks `env` and crash
  isolation between services; (c) `worker_threads` instead of `fork` (~10 MB instead of 48 MB) — a
  big win, but it requires revisiting `process.env` and `process.exit` isolation for the handlers.
  **(c) is the natural next step if 128 MB + N×48 MB is still uncomfortable.**

### 4.2 `idleTimeoutMs` defaulting to **60 s** and `maxWarmWorkers` to **1 per GB of RAM**

- **I chose:** aggressive, as you specified — a lambda comes up when it is used and goes down
  afterwards. A cold start costs 23 ms; slowness is not the problem, locking up the host is.
- **Why both, and not just the timeout:** the timeout alone does not protect against a burst. A test
  suite or a boot script that touches all 40 services within the idle window would have all 40
  workers alive at once. The ceiling is what turns "memory proportional to registered services" into
  "memory proportional to services in use".
- **Alternatives for the ceiling:** (a) a fixed value (say 8) — predictable, but it either wastes on
  a big machine or suffocates on a small one; (b) a budget in MB instead of a process count — more
  precise, but it needs periodic RSS sampling of the children; (c) no ceiling (`0`), trusting the
  timeout alone. I chose 1/GB clamped to 2..12 because it answers "it must not lock up the host
  computer" directly, with no per-machine configuration.

### 4.3 The `idle` status reported as `online` + `warm: false`

- **I chose:** keep `status` stable and add `warm`. Zero change for existing consumers, and the new
  information is there for the UI to use.
- **Alternative:** expose `idle` directly in `runtimeStatus` — more honest, but it would break the
  UI (the status badge), the typed client and the route tests.

### 4.4 `persistence:false` → an in-memory store (and not a temp directory)

- **I chose:** a dedicated in-memory implementation. It is what the documentation promises and it
  gives a real clean slate.
- **Alternatives:** (a) point `dataDir` at a temp dir deleted on shutdown — less code, but it still
  does I/O and leaks the directory on a SIGKILL; (b) make the writes a no-op inside `JsonlItemTable`
  — that would touch the tested critical WAL path.
- **Trade-off taken and documented:** in in-memory mode the S3 bodies live in the heap (the on-disk
  store keeps them out of it) and `idleUnloadMs`/`memoryBudgetMb` go inert — discarding a table
  without a snapshot would be data loss, not eviction.

### 4.5 CLI: only the LocalStack variables were removed in self mode

- **I chose:** remove only the `LSS_LOCALSTACK_*`/token when `engine === 'self'`.
- **I did not:** stop exporting `PORT` and `LSS_DYNAMO_PROXY_PORT`. That would make `serverPort` and
  `dynamoProxyPort` editable in the Settings tab, but it would change `LSS_CONFIG_PATH`'s documented
  passthrough contract and touch the most test-covered file in the repo.
- **Recommended alternative for a next step:** always export `LSS_CONFIG_PATH` with the resolved
  config file (including when found through the cwd/home search) and stop translating config → env,
  keeping env **only** for what came from a CLI flag (`--external`, `--pro`, `--localstack-token`,
  `--self-engine`, `--enable-dynamo-proxy`). Then `envOverrides` goes back to meaning "the user set
  an env var".

## 5. Prioritised backlog — what I did **not** fix

It came out of a multi-agent audit (7 dimensions × adversarial verification): 89 confirmed findings.
Below are the ones left, ordered by impact on your scenario. Each item has a recommendation and,
where one exists, an alternative path.

### P0 — they hit the 40-service monorepo directly

**1. No lock on the engine's `dataDir`** (`engine/store/engine-store.ts`)
Two engines pointing at the same directory corrupt each other **silently** (no error). It happens
with a project copy, a worktree with a symlinked `.lss`, or two `lss start`s in the same folder on
different ports.
→ *Recommended:* an exclusive `<dataDir>/engine.lock` through `fs.openSync(p,'wx')` carrying
`{pid, serverPort, enginePort}`; if the pid is alive, abort with the same message quality as
`EADDRINUSE`; if it is dead, take the lock and log the recovery. And make `atomic.ts`'s `tmpPath`
unique per process.
→ *Alternative:* just the unique `tmpPath` + a warning — but WAL truncation by `compact()` keeps
happening.

**2. `GET /api/config` fabricates a `localstack` block in self mode**
(`routes/config.ts:42`) — I fixed the UI, but the payload still carries `endpoint: :4566`,
`image: localstack/localstack:latest`, `mode: managed`. Every other API consumer is still misled.
→ *Recommended:* `localstack: null` in self mode (easier for a typed consumer than omitting the key)
and adjust `LssConfigSnapshot` in the client and the UI.

**3. DynamoDB Query/Scan materialises the whole table and sorts it on every call; GSI/LSI are never
materialised** (`engine/emulators/dynamodb/query.ts:243`)
With 400 tables and real data volume, this is the most likely CPU bottleneck.
→ *Recommended:* keep an index sorted by partition key at hydration time, and materialise GSIs as
secondary structures maintained on `put`/`delete`.
→ *Cheap alternative:* cache the sort per table, invalidated on write — it solves the repeated Scan
without touching the structure.

**4. `memoryBudgetMb` counts JSON length, not heap** (`engine/store/wal.ts:53`)
The 128 MB default is worth ~390 MB of heap / ~540 MB of real RSS. On a weak machine the budget does
not protect what it promises.
→ *Recommended:* calibrate the factor (measure `process.memoryUsage()` against `approxBytes` on a
synthetic table) and document the real unit, or switch to heap sampling.

**5. `lambdaRuntime.enabled: false` still provisions ESMs and proxies**
(`services/service-registrar.ts:187`) — the engine tries to deliver forever and arms a 1 s timer per
ESM. I confirmed that workers and listeners stay at 0, but the delivery loops do not.
→ *Recommended:* skip event-source-mapping provisioning when the runtime is off for that service.

**6b. `idleTimeoutMs` does not cover a worker dying in a crash-restart loop** — the `MAX_RESTARTS`
counter (3 in 30 s) already caps it, but a service that breaks on import restarts 3× before giving
up. With 40 services on a bad boot, that is up to 120 forks.
→ *Recommended:* do not auto re-fork when the worker never reported `ready` (an import failure) —
only when it had been online.

**6. `QueueInspector.startPolling()` always runs** (`index.ts:124`) — 1+N AWS requests every 5 s
regardless of whether there is a queue, an open dashboard or `sqs` in `services`.
→ *Recommended:* only start it when a queue is registered, and stop after N cycles with no consumer
of `/api/queues`.

### P1 — automated tests (your third objective)

**7. There is no ephemeral port for the orchestrator** (`config-manager.ts:437`)
`serverPort: 0` is rejected and the real port is never published. That makes
`jest --maxWorkers=N` with one stack per worker unworkable: it would mean allocating ~80 ports per
stack by hand.
→ *Recommended:* accept `0`, and on boot write `<stateDir>/orchestrator.json` with the resolved
ports (orchestrator, engine, and `apiPort`/`invokePort` per service); the client's `resolveConfig()`
starts reading that file.
→ *Cheaper alternative:* an `LssClient.ephemeral()` that reserves free ports in the test process and
writes a temporary config (subject to TOCTOU, solves 95%).

**8. `waitUntilReady()` returns before the seeds and `rehydrateAll()`** (`index.ts`)
The test's *arrange* races the boot.
→ *Recommended:* only mark `status: 'ok'` on `/api/health` after seeds + rehydrate, or add a `ready`
field separate from `status`.

**9. The client's `lifecycle.start()` cannot boot the self engine** (`client/lifecycle.ts:10`)
It only exposes LocalStack flags and pays a fixed `setTimeout(2000)` per boot.
→ *Recommended:* add `engine: 'self'` to `StartOptions` and swap the fixed sleep for a poll on
`/api/health`.

**10. There is a waiting primitive for SQS only** (`routes/queues.ts:64`)
There is no way to await EventBridge, DynamoDB Streams, an S3 notification or the end of an
invocation.
→ *Recommended:* `POST /api/lambdas/:name/await-invocations { count, timeoutMs }` — wait for the
**effect** (the lambda ran N times), which is deterministic, rather than for the cause.
→ This also solves item 11.

**11. `sinceProcessed` is derived from a sampling heuristic** (`queue-inspector.ts:612`)
The **faster** the consumer, the more likely `awaitIdle({sinceProcessed:1})` never satisfies the
condition and spins until the deadline.
→ *Recommended:* an exact monotonic per-queue deletion counter in `SqsEmulator`, exposed through an
attribute/endpoint; keep the heuristic on the LocalStack path only.

**12. There is no state reset between tests** (`services/seed-manager.ts:291`)
`seeds.clear` only wipes tables that have a seed file, and it does a Scan + BatchDelete item by item.
→ *Recommended:* `POST /api/engine/reset` recreating the store (trivial now that the in-memory store
exists). With `persistence:false` the reset is already "restart the process".

**13. `SelfEngineBackend` is not exported by the published package** (`package.json:12`)
It is the pattern the repo's own `wire-*` tests use, but users have no access to the in-process mode.
→ *Recommended:* export it under `exports` as `./engine` and document the pattern.

**14. Zero e2e coverage of the self engine** (`tests/integration/`)
The only integration suite is gated on Docker + `LOCALSTACK_AUTH_TOKEN`.
→ *Recommended:* an integration suite with `engine: 'self'` — it needs neither Docker nor a token,
so it runs in any CI.

### P2 — quality, docs and UI

**15. The "100% global coverage" gate excludes `src/server/engine/**` and `src/server/runtime/**`**
(`jest.config.js:9`) — 47 files / ~13 thousand lines, including the product's entire differentiator.
The tests exist (45 of the 92 test files are the engine's); what is missing is the **measurement**:
`npm run test:coverage` passes at 100% even with a new WAL/LRU/FilterCriteria branch untested. The
file's other 6 exclusions carry a comment explaining why; these two are by omission.
→ *Recommended:* add them to `collectCoverageFrom` with explicit, commented exclusions, and a
per-path `coverageThreshold` starting at the measured value and ratcheting up.
→ *Minimum alternative:* fix AGENTS.md §3's text to list what is outside.

**16. `DELETE /api/services/:name` deletes real AWS resources** (`routes/services.ts:181`)
With 10 tables per service, removing a service from the dashboard destroys 10 tables and the seeded
data, with no confirmation and with none of the 4 documents warning about it. `lss seed:clear`,
which is far less destructive, has an interactive confirmation.
→ *Recommended:* document it + require `?deleteResources=true` + a confirmation in the UI.
→ *Alternative:* split it into `DELETE /:name` (deregister only) and `DELETE /:name/resources`.

**17. `engine` defaults to `'localstack'` in three places**, and the `lss.config.json` committed at
the repo root boots Docker. The product's differentiator is opt-in behind a flag.
→ *Recommended (immediate, no breaking change):* switch the root `lss.config.json` to
`engine: "self"`. The repo starts developing on its own differentiator.
→ *Recommended (major):* invert the default and add the symmetric `lss start --localstack` flag.

**18. No list in the UI has pagination or virtualisation** and 5 of 8 have no filter
(`ui/src/components/lambdas/LambdasList.vue:123`). With 2,400 lambdas the tab freezes on a weak
machine — exactly the target audience.
→ *Recommended:* since table pagination belongs to TreeUI, take the request for a `TTable` with
`page-size`/`virtualized` to the library.
→ *Stopgap with no local CSS:* slice to the first 100 rows in a `computed` + a "showing 100 of 2400,
refine the filter" counter.

**19. Fixed-interval polling in the UI, with no pause on a hidden tab**
(`ui/src/components/QueuesView.vue:82`) — with 40 services, the Queues tab forces ~40 CloudFormation
template reads and parses **every 4 s**, even minimised.
→ *Recommended:* a `usePolling(fn, ms)` composable that respects `document.hidden`; fetch
`listResourceOwners()` once per mount; memoise the parse by `templateHash` on the server.

**20. `POST /register` overwrites a service by name with no warning**
(`services/function-registry.ts:59`) — two checkouts of the same repo register with the same
orchestrator (`orchestratorUrl` is hardcoded in `serverless.yml`); the second repoints the service's
`root` at the other tree.
→ *Recommended:* an explicit warning when the root changes, and a 409 by default when the new root
is outside `projectRoot`.

**21. `dist/server/index.js` is ESM without `"type": "module"`** (`package.json`)
Every boot prints `MODULE_TYPELESS_PACKAGE_JSON` and pays a reparse for syntax detection — for the
orchestrator **and for every worker**. It shows up in every log the product produces.
→ *Recommended:* settle the published package's `"type"` (or emit `.mjs`).

**22. No performance harness in the repo.** The numbers in §1 have nothing watching them.
→ *Recommended:* move `gen-scale.js`/`run-scale.sh` into `tests/perf/` with a floor (e.g. fail if
the RSS of 40 idle services passes 300 MB).

**Smaller ones** (all with file:line in the audit report): `lss status` and `lss seed:clear` print
"LocalStack: http://localhost:4566" unconditionally; `lss help` documents only LocalStack
configuration; the client's `HealthStatus`/`StartOptions` do not expose the engine;
`lambdas.invoke(…, {invocationType:'Event'})` returns a shape different from the declared type; the
aoss sidecar switch on the SettingsPage is a silent no-op in self mode; `BucketDetail` truncates at
200 objects without saying so; `debug` is a dead toggle on the self engine but the UI presents it as
"Verbose engine logging"; `selfEngine.account` is honoured by the engine but hardcoded to
`000000000000` in the provisioner; the `secrets` key is missing from `CONFIGURATION.md`;
`/_lss/health` is undocumented; 76 inline `style=` violating the TreeUI contract with no gap

## 5b. Second round — v0.18.0, MCP, the logo and the 1.0 verdict

### The bump

`0.17.2 → **0.18.0**` (root + lockfile). A minor, not a patch: the Lambda runtime's residency
defaults change observable behaviour, and there is new API surface (`warm`, `runtimeWarm`,
`engineRunning`, a 404 on `/api/*`) plus the MCP server. The `serverless-lss` plugin stays at
`0.2.2` — nothing in it changed. **There is no pre-commit hook in the repo** (`.git/hooks` holds
only samples, no husky/lint-staged); the gate I ran is `validate: pre-prod`.

### The 1.0 criterion — tested, not estimated

You made 1.0 conditional on "running everything we support on LocalStack Ultimate in self mode". I

### The "Live load" panel on the Overview

parallel**, so you can tell how much of the machine is being pulled.

**Server.** `src/server/services/invocation-activity.ts` — a global ring of spans (service,
function, start, duration, ok, cold start), capped at 1000, with **no logs** (the per-service
`history` that already existed carries the captured logs and is scoped to one service; it is no use
for "what ran in parallel across services"). `GET /api/lambdas/activity?windowMs=&buckets=` joins
that with the worker table, the residency policy and the host's counters.

Two decisions worth recording:
- **Parallelism is the PEAK per bucket, never the average.** A 300 ms burst that saturates the
  machine is exactly what an average erases.
- **A span that started before the window and is still running counts.** A 5-minute handler IS the
  load; filtering by `startedAt >= from` would show an idle stack.

**UI.** `src/ui/src/components/ActivityPanel.vue`: tiles (resident workers / ceiling, peak
parallelism, host memory, per-core normalised load), a stepped area chart of parallelism, and a
timeline with one lane per service and one bar per invocation — overlapping bars in the same
vertical slice **are** the parallelism.

Two visualisation decisions, which are decisions and not taste:
- **Identity goes on the lane axis, not on colour.** With 40 services there is no legible
  categorical palette (TreeUI exposes 8 slots); so the colour is a single one.
- **Failure is not encoded by colour alone.** I measured it: TreeUI's `status-success` and
  `status-error` sit at **ΔE 4.4 under deuteranopia** — colour alone would hide every error from a
  colourblind reader. An error gets a shape marker + a labelled count on top of the colour.

**"When I turn something off, does it leave junk behind?"** `lambdaRuntime.enabled:false` was clean
(0 workers, 0 listeners) except for the ESMs (item 5). `persistence:false` did leave junk and was
fixed. `aossSidecar` was already correctly off in self mode. `enableDynamoProxy:false` opens
nothing. The junk that remained was cumulative in `~/.lss` — fixed by scoping per project; what is
left is only the flat legacy cache (`~/.lss/orchestrator/cache/<service>`) from old versions, which
is never cleaned and is invisible to the current code.

**"Good isolation between environments?"** Yes, as long as you use `stateDir` (which the examples
do). Without `stateDir` it was shared globally — fixed. The hole that remains is the absence of a
lock (item 1).

**"Two processes in parallel without breaking?"** Proven: two complete instances, four services
each, fully isolated data, `stop` on one not touching the other. The conditions are distinct ports
for everything (orchestrator, engine, `apiPort`, `invokePort`) and a `stateDir` of its own. What
still breaks: `artifact` mode sharing an extraction directory (fixed) and the same hardcoded
`orchestratorUrl` in `serverless.yml` making two checkouts register with the same orchestrator
(item 20).

**"Can it be used in automated tests?"** Today, for a **serial** suite against a fixed stack, yes —
and `awaitIdle` now works deterministically. For the pattern you will want (N stacks in parallel,
one per Jest worker, a clean slate per run), items 7, 8, 10 and 12 are missing. With
`persistence:false` fixed, the clean slate is already possible today by restarting the process.

**"Does the self host carry LocalStack cruft?"** It did, plenty — env vars, UI text on every screen,
the `:4566` endpoint displayed as if it were the real one, a `localstack` field in health. Most of
it is fixed. What remains is the fabricated `localstack` block in `/api/config` (item 2), the CLI's
text and the `engine: 'localstack'` default (item 17). The static `LocalStackBackend` import in
`engine-manager` exists, but the module only imports `child_process` — a negligible cost; it is the
file's comment that overstates the asymmetry.

**"Is it heavy?"** After the fixes: **128 MB idle with 40 services registered**, +48 MB per service
actually invoked, 0.3% idle CPU, a 2 s boot, registration at 22 ms per service. With
`idleTimeoutMs` on, the ceiling sits at the number of services you use at once, not the number you
have.
