# Revisão do LSS — 2026-07-29

Documento de handoff. **Nada foi commitado**: tudo está na working tree para você revisar.
As duas primeiras seções são o que interessa se você tiver 5 minutos.

---

## 1. Resumo executivo

Subi o stack de verdade (exemplo `self-hosted`, engine self, sem Docker), dirigi o pipeline
ponta a ponta, rodei duas instâncias em paralelo e montei um projeto sintético de **40 serviços
× 400 lambdas × 400 tabelas** para medir o cenário que motiva o projeto.

**O produto funciona.** O pipeline `POST /orders → DynamoDB → SQS → Lambda → S3 + EventBridge →
regra → Lambda → DynamoDB` roda inteiro em ~120 ms, o redrive para DLQ respeita
`maxReceiveCount`, OpenSearch responde busca e agregação, persistência sobrevive a restart e
duas instâncias paralelas ficam completamente isoladas. Boot em 2 s, registro de 40 serviços
em 0,9 s (22 ms cada), latência de API abaixo de 200 ms com 400 tabelas.

**Mas havia quatro problemas que batem exatamente no seu caso de uso**, todos corrigidos:

| # | Problema | Efeito no seu monolito de 40 OSLs |
|---|---|---|
| 1 | Um worker Node forkado **ansiosamente** por serviço registrado | **2,0 GB de RAM parada** antes de qualquer handler rodar |
| 2 | `ListTables` sem paginação (AWS corta em 100) | Das suas **400 tabelas, só 100 apareciam** no dashboard e na API |
| 3 | Explorers com região default `us-east-1` fixa | Projeto fora de us-east-1 → **API devolvia listas vazias** (o dashboard escapava; CLI/`LssClient`/curl não) |
| 4 | `persistence: false` era **no-op** no self engine | Sem clean slate para teste automatizado; deixava `.lss/engine/` para trás |

Medição do antes/depois com 40 serviços registrados, ociosos:

| | antes | depois |
|---|---|---|
| RSS total da instância | **2.020 MB** | **128 MB** (−94%) |
| processos worker | 40 | 0 parado; teto de `maxWarmWorkers` em uso |
| CPU ociosa | 4,1% | 0,3% |
| tabelas listadas (de 400) | 100 | 400 |
| cold start da 1ª invocação | — | **~23 ms** (morno: ~1 ms) |
| watches inotify por serviço | 1.756 | 4 |

O gate `validate: pre-prod` passa inteiro: lint 0 erros, `tsc` nos 4 projetos, **2.462 testes
verdes com cobertura 100%**, build completo.

## 3. Alterações aplicadas

Agrupadas por tema. Todas com teste e comentário explicando o *porquê*, no estilo da base.

### 3.1 Escala — worker sob demanda (a mudança de maior impacto)

**`src/server/services/lambda-runtime-manager.ts`, `config-manager.ts`, `routes/{lambdas,services}.ts`**

`syncService()` forkava o worker no registro. Agora resolve onde os handlers moram (então um
artefato quebrado **continua falhando no registro**, não na primeira chamada) e deixa o fork
para o primeiro `invoke`.

- `lambdaRuntime.lazy` — **default `true`**. `false` restaura o comportamento antigo.
- `lambdaRuntime.idleTimeoutMs` — **default `60000`** (1 min). Descarrega um worker que ficou
  quieto; nunca interrompe invocação em voo. `0` mantém vivo para sempre.
- `lambdaRuntime.maxWarmWorkers` — **default: 1 por GB de RAM, limitado a 2..12**. Teto rígido
  de workers residentes; ao estourar, descarrega o menos recentemente invocado. É o que garante
  que a memória do host depende dos serviços **em uso**, não dos serviços **registrados** — uma
  rajada que toca os 40 dentro da janela de ociosidade ainda estabiliza no teto.

Medido no stack sintético de 40 serviços, com `maxWarmWorkers: 4` e `idleTimeoutMs: 8000`:

| momento | workers | RSS |
|---|---|---|
| 40 registrados, nada invocado | 0 | **128 MB** |
| logo após invocar **todos os 40** em rajada | **4** (teto) | 329 MB |
| 11 s depois, ocioso | **0** | **132 MB** |
| requisição seguinte | re-fork | 200 em **23 ms** |

- Status interno novo `idle`, mas `getRuntimeInfo()` reporta `online` + `warm: false` — nenhum
  consumidor (UI, rotas, dispatch) precisou mudar, porque para todos eles "idle" significa
  "vai atender". `GET /api/lambdas` expõe `warm`, `GET /api/services` expõe `runtimeWarm`.

### 3.2 Escala — WAL, watchers e paginação

- **`src/server/engine/store/wal.ts`** — compactação só acontecia via `dehydrate()`, que é
  disparado pelo sweep de ociosidade e pelo LRU. Uma tabela escrita continuamente nunca fica
  ociosa: o WAL crescia a sessão inteira e era relido por completo no boot seguinte. Agora a
  tabela compacta sozinha quando o WAL passa de 4 MB **e** do dobro do tamanho residente.
- **`src/server/services/source-watcher.ts`** — `fs.watch(root, {recursive:true})` registra um
  watch inotify por diretório da árvore. Medido no exemplo: **1.756 diretórios, dos quais 4 têm
  código**. Com 40 serviços seriam ~70 mil watches (`max_user_watches` costuma ser 8.192 em
  máquina de dev). `IGNORED_SEGMENTS` só filtrava os eventos, nunca os watches. Agora: watch
  não-recursivo na raiz + um recursivo por subdiretório não ignorado.
- **Paginação** em `dynamo-explorer.ts`, `seed-manager.ts`, `resource-provisioner.ts`
  (`ListTables`, corte em 100) e `queue-inspector.ts` + `resource-provisioner.ts`
  (`ListQueues`, corte em 1000). O engine implementa o corte fielmente à AWS — o bug era do
  consumidor.

### 3.3 Correção de região nos explorers

**`src/server/services/explorer-region.ts` (novo)** + construtores de `dynamo-explorer`,
`secrets-explorer`, `opensearch-explorer`.

`DynamoExplorer`, `SecretsExplorer` e `OpenSearchExplorer` tinham `defaultRegion = 'us-east-1'`
fixo e `setDefaultRegion()` nunca era chamado no boot (só `SeedManager` chamava).
`S3Explorer`/`QueueInspector` já liam a região do engine no construtor — a inconsistência
escondia o bug. O dashboard sempre manda `?region=` (lido de `/api/config`), então só quebrava
para **CLI, `LssClient` e curl**. Agora: construtor lê a região configurada, `index.ts` fixa
explicitamente no boot, e `PUT /api/config` / `POST /api/config/reload` re-aplicam.

Sintoma antes da correção, no exemplo shipado (região `us-west-2`):

```
$ curl .../api/dynamo/tables        → {"tables":[]}
$ curl .../api/dynamo/tables?region=us-west-2  → 2 tabelas
```

### 3.4 `persistence: false` passou a significar o que promete

**`src/server/engine/store/memory-store.ts` (novo)**, `engine-store.ts`, `self-backend.ts`.

`config.persistence` só era consultado para o snapshot de mensagens SQS. Catálogos e WAL eram
escritos sempre — tabelas e filas sobreviviam ao restart e o run deixava `.lss/engine/` para
trás. Agora `persistence: false` troca o store por um in-memory: nada é criado em disco,
nenhum boot herda estado.

Verificado: com `persistence:false`, `.lss/` contém só `orchestrator.{log,pid}`, e
`/api/resources` volta vazio depois de um restart.

### 3.5 Isolamento entre projetos e instâncias

- **`src/server/services/project-scope.ts` (novo)** — `projectCacheSegment()` saiu de
  `cache-manager.ts` (re-exportado de lá, sem quebrar importadores) para poder ser usado sem
  ciclo de import.
- **`config-manager.ts`** — novo env var **`LSS_ENGINE_DATA_DIR`**: com ele, mais
  `LSS_DASHBOARD_PORT` e `LSS_ENGINE_PORT`, uma segunda instância sobe sem escrever nenhum
  arquivo de config e sem compartilhar nada com o stack de dev:
  ```bash
  LSS_DASHBOARD_PORT=3250 LSS_ENGINE_PORT=14766 \
    LSS_ENGINE_DATA_DIR=/tmp/lss-run-7/engine npx lss start --self-engine
  ```
  Validado: o estado do engine foi inteiro para o diretório do env e `.lss/` ficou só com
  `orchestrator.{log,pid}`.
- **`config-manager.ts`** — sem `stateDir`, `dataDir` do engine e do sidecar aoss caíam em
  `~/.lss/engine` e `~/.lss/aoss`, **globais**: todo projeto da máquina compartilhava o mesmo
  conjunto de tabelas. Agora: `~/.lss/projects/<slug>-<hash>/{engine,aoss}`.
- **`lambda-runtime-manager.ts`** — o diretório de extração de artefato era
  `~/.lss/orchestrator/runtime/<serviceName>/<hash>`, sem escopo de projeto, e um registro novo
  faz `rm -rf` do diretório base. Dois checkouts com um serviço chamado `api` → o segundo
  apagava o código do qual o worker do primeiro estava rodando. Agora escopado por projeto.
- **`bin/cli.js`** — `lss start` com `engine: "self"` não exporta mais nenhuma
  `LSS_LOCALSTACK_*` nem `LOCALSTACK_AUTH_TOKEN`. Além do vazamento (o env é herdado por todo
  worker forkado), cada chave exportada era reportada por `GET /api/config` como
  `envOverridden` — o que **acinzentava 7 campos na aba Settings** para valores que você nunca
  setou.

### 3.6 Erros que derrubavam o processo

- **`src/server/index.ts`** — `app.listen()` sem handler de `error`: um `EADDRINUSE` na porta
  do dashboard virava exceção não tratada **depois** de o engine já ter feito bind da porta
  dele e armado os loops de entrega, deixando um processo meio vivo. Agora: mensagem nomeada +
  shutdown limpo com exit code 1.
- **`src/server/dev/dynamo-proxy.ts`** — mesmo problema; como o proxy é opcional, degrada para
  warning e o orquestrador continua de pé.

### 3.7 Testabilidade

- **`src/client/{http,namespaces/queues}.ts`** — o default de `awaitIdle` no servidor (15.000 ms)
  era **igual** ao timeout HTTP default do `LssClient` (15.000 ms): a principal primitiva de
  espera do produto resolvia ou lançava dependendo de escalonamento. Agora o request de
  `awaitIdle` tem orçamento próprio (`timeoutMs` do servidor + 5 s de folga).
- **`src/server/index.ts`** — qualquer `/api/*` que nenhum router reivindicou agora responde
  **404 JSON**, não o `200 text/html` do SPA. Antes, um path errado passava por sucesso para
  curl, para o `LssClient` e para qualquer teste assertando na resposta.
- **`tests/unit/engine/dispatch/helpers.ts`** — causa raiz do flake `ENOTEMPTY` documentado no
  AGENTS.md: `cleanup()` fazia `rm -rf` sem `flushAll()`, correndo com as escritas debounced
  (20 ms) do catálogo. Agora drena antes e tem retry curto. Confirmei que o flake é de
  **contenção de CPU**: ele reapareceu enquanto a instância de 40 workers rodava e sumiu depois
  — 5 execuções limpas seguidas.

### 3.8 Dashboard sem "LocalStack" no modo self

**`src/ui/src/services/engine.ts` (novo)** + `App.vue`, `OverviewPage.vue`, `QueuesView.vue`,
`BucketsView.vue`, `ServicesList.vue`, `ServiceDetailPage.vue`, `api.ts`.

O badge do header dizia "LocalStack: Running" sempre; a Overview dizia "One LocalStack. Every
microservice." e mostrava `endpoint: :4566` / `image: localstack/localstack:latest` / `mode:
managed` **mesmo com o engine self em :14666** — o campo que o dev copia para o SDK apontava
para uma porta morta. Empty states e confirmações de exclusão diziam "in LocalStack".

Agora tudo lê `engineLabel`/`isSelfEngine`, alimentados por `/api/health` (`engine.kind`) e
`/api/config`. No servidor, `GET /api/health` ganhou `engineRunning`; `localstack` continua como
alias deprecado.

`README.md`, `docs/FEATURES.md`, `docs/SELF_ENGINE.md`, `docs/CONFIGURATION.md` atualizados
para tudo acima (exigência do AGENTS.md §4).

## 4. Decisões que tomei — e as alternativas

Você pediu para eu escolher e listar as alternativas.

### 4.1 `lambdaRuntime.lazy` default **true**

- **Escolhi:** ligado por default. É a diferença entre 2,0 GB e 128 MB no seu cenário, e o custo
  medido é 23 ms na primeira chamada de cada serviço.
- **Alternativas:** (a) default `false` e opt-in — mais conservador, mas ninguém liga o que não
  sabe que existe, e o cenário-alvo do produto é justamente o que sofre; (b) worker
  multi-tenant (N serviços por processo) — economiza mais, mas quebra o isolamento de `env` e
  de crash entre serviços; (c) `worker_threads` em vez de `fork` (~10 MB em vez de 48 MB) —
  ganho grande, mas exige revisar isolamento de `process.env` e de `process.exit` dos handlers.
  **(c) é o próximo passo natural se 128 MB + N×48 MB ainda incomodar.**

### 4.2 `idleTimeoutMs` default **60 s** e `maxWarmWorkers` default **1 por GB de RAM**

- **Escolhi:** agressivo, conforme você definiu — o lambda sobe quando é usado e cai depois.
  Um cold start custa 23 ms; lentidão não é problema, travar o host é.
- **Por que os dois, e não só o timeout:** o timeout sozinho não protege de uma rajada. Uma
  suíte de testes ou um script de boot que toca os 40 serviços dentro da janela de ociosidade
  teria os 40 workers vivos ao mesmo tempo. O teto é o que transforma "memória proporcional aos
  serviços registrados" em "memória proporcional aos serviços em uso".
- **Alternativas para o teto:** (a) valor fixo (ex.: 8) — previsível, mas ou desperdiça numa
  máquina grande ou sufoca numa pequena; (b) orçamento em MB em vez de contagem de processos —
  mais preciso, mas exige amostrar RSS dos filhos periodicamente; (c) sem teto (`0`), confiando
  só no timeout. Escolhi 1/GB limitado a 2..12 porque responde diretamente ao "não pode travar
  o computador hospedeiro" sem precisar de configuração por máquina.

### 4.3 Status `idle` reportado como `online` + `warm: false`

- **Escolhi:** manter `status` estável e adicionar `warm`. Zero mudança para consumidores
  existentes, e a informação nova está lá para a UI usar.
- **Alternativa:** expor `idle` diretamente em `runtimeStatus` — mais honesto, mas quebraria a
  UI (badge de status), o client tipado e testes de rota.

### 4.4 `persistence:false` → store in-memory (e não diretório temporário)

- **Escolhi:** implementação in-memory dedicada. É o que a documentação promete e dá clean
  slate real.
- **Alternativas:** (a) apontar `dataDir` para um temp dir apagado no shutdown — menos código,
  mas continua fazendo I/O e vaza o diretório num SIGKILL; (b) tornar as escritas no-op dentro
  do `JsonlItemTable` — mexeria no caminho crítico de WAL testado.
- **Trade-off assumido e documentado:** em modo in-memory os corpos de S3 ficam no heap
  (o store em disco os mantém fora dele) e `idleUnloadMs`/`memoryBudgetMb` ficam inertes —
  descartar uma tabela sem snapshot seria perda de dados, não evicção.

### 4.5 CLI: só as variáveis de LocalStack foram removidas no modo self

- **Escolhi:** remover apenas as `LSS_LOCALSTACK_*`/token quando `engine === 'self'`.
- **Não fiz:** parar de exportar `PORT` e `LSS_DYNAMO_PROXY_PORT`. Isso deixaria `serverPort`
  e `dynamoProxyPort` editáveis na aba Settings, mas mudaria o contrato documentado do
  `LSS_CONFIG_PATH` passthrough e mexe no arquivo mais coberto por teste do repo.
- **Alternativa recomendada para um próximo passo:** sempre exportar `LSS_CONFIG_PATH` com o
  arquivo de config resolvido (inclusive quando encontrado pela busca em cwd/home) e deixar de
  traduzir config → env, mantendo env **só** para o que veio de flag de CLI
  (`--external`, `--pro`, `--localstack-token`, `--self-engine`, `--enable-dynamo-proxy`).
  Aí `envOverrides` volta a significar "o usuário setou um env var".

## 5. Backlog priorizado — o que **não** corrigi

Saiu de uma auditoria multi-agente (7 dimensões × verificação adversarial): 89 achados
confirmados. Abaixo os que sobraram, em ordem de impacto no seu cenário. Cada item tem a
recomendação e, quando existe, o caminho alternativo.

### P0 — mexem direto no monolito de 40 serviços

**1. Sem lock no `dataDir` do engine** (`engine/store/engine-store.ts`)
Dois engines apontando para o mesmo diretório se corrompem em **silêncio** (não dá erro).
Acontece com cópia de projeto, worktree com `.lss` symlinkado, ou dois `lss start` na mesma
pasta com portas diferentes.
→ *Recomendado:* lock exclusivo `<dataDir>/engine.lock` via `fs.openSync(p,'wx')` com
`{pid, serverPort, enginePort}`; se o pid estiver vivo, abortar com a mesma qualidade de
mensagem do `EADDRINUSE`; se morto, tomar o lock e logar recuperação. E tornar o `tmpPath` de
`atomic.ts` único por processo.
→ *Alternativa:* só o `tmpPath` único + aviso — mas a truncagem de WAL pelo `compact()`
continua acontecendo.

**2. `GET /api/config` fabrica um bloco `localstack` no modo self**
(`routes/config.ts:42`) — corrigi a UI, mas o payload ainda traz `endpoint: :4566`,
`image: localstack/localstack:latest`, `mode: managed`. Qualquer outro consumidor da API
continua sendo enganado.
→ *Recomendado:* `localstack: null` no modo self (mais fácil para consumidor tipado que omitir
a chave) e ajustar `LssConfigSnapshot` no client e na UI.

**3. Query/Scan do DynamoDB materializa a tabela inteira e ordena a cada chamada; GSI/LSI nunca
são materializados** (`engine/emulators/dynamodb/query.ts:243`)
Com 400 tabelas e volume real de dados, é o gargalo de CPU mais provável.
→ *Recomendado:* manter um índice ordenado por partition key na hidratação e materializar GSI
como estruturas secundárias mantidas no `put`/`delete`.
→ *Alternativa barata:* cachear a ordenação por tabela, invalidada na escrita — resolve o
Scan repetido sem tocar na estrutura.

**4. `memoryBudgetMb` conta comprimento de JSON, não heap** (`engine/store/wal.ts:53`)
O default de 128 MB vale ~390 MB de heap / ~540 MB de RSS reais. Numa máquina fraca, o
orçamento não protege do que promete.
→ *Recomendado:* calibrar o fator (medir `process.memoryUsage()` contra `approxBytes` numa
tabela sintética) e documentar a unidade real, ou trocar por amostragem de heap.

**5. `lambdaRuntime.enabled: false` continua provisionando ESMs e proxies**
(`services/service-registrar.ts:187`) — o engine tenta entregar para sempre e arma um timer de
1 s por ESM. Confirmei que worker e listeners ficam em 0, mas os loops de entrega não.
→ *Recomendado:* pular o provisionamento de event-source-mapping quando o runtime está
desligado para aquele serviço.

**6b. `idleTimeoutMs` não cobre worker que morre por crash-restart em loop** — o contador
`MAX_RESTARTS` (3 em 30 s) já limita, mas um serviço que quebra no import fica reiniciando 3×
antes de parar. Com 40 serviços num boot ruim, são até 120 forks.
→ *Recomendado:* não re-forkar automaticamente quando o worker nunca chegou a reportar `ready`
(falha de import) — só quando ele já esteve online.

**6. `QueueInspector.startPolling()` roda sempre** (`index.ts:124`) — 1+N requisições AWS a cada
5 s independentemente de haver fila, dashboard aberto ou `sqs` nos `services`.
→ *Recomendado:* só ligar quando houver fila registrada, e desligar após N ciclos sem
consumidor de `/api/queues`.

### P1 — testes automatizados (seu terceiro objetivo)

**7. Não existe porta efêmera para o orquestrador** (`config-manager.ts:437`)
`serverPort: 0` é rejeitado e a porta real nunca é publicada. Isso inviabiliza
`jest --maxWorkers=N` com um stack por worker: seriam ~80 portas por stack para alocar à mão.
→ *Recomendado:* aceitar `0`, e ao subir gravar `<stateDir>/orchestrator.json` com as portas
resolvidas (orquestrador, engine, e `apiPort`/`invokePort` por serviço); `resolveConfig()` do
client passa a ler esse arquivo.
→ *Alternativa mais barata:* `LssClient.ephemeral()` que reserva portas livres no processo de
teste e escreve um config temporário (sujeito a TOCTOU, resolve 95%).

**8. `waitUntilReady()` retorna antes dos seeds e do `rehydrateAll()`** (`index.ts`)
O *arrange* do teste corre contra o boot.
→ *Recomendado:* só marcar `status: 'ok'` no `/api/health` depois de seeds + rehydrate, ou
adicionar um campo `ready` separado do `status`.

**9. `lifecycle.start()` do client não sabe subir o self engine** (`client/lifecycle.ts:10`)
Só expõe flags de LocalStack e paga um `setTimeout(2000)` fixo por boot.
→ *Recomendado:* adicionar `engine: 'self'` às `StartOptions` e trocar o sleep fixo por poll no
`/api/health`.

**10. Só existe primitiva de espera para SQS** (`routes/queues.ts:64`)
Não há como aguardar EventBridge, DynamoDB Streams, notificação S3 ou o fim de uma invocação.
→ *Recomendado:* `POST /api/lambdas/:name/await-invocations { count, timeoutMs }` — espera pelo
**efeito** (a lambda rodou N vezes), que é determinístico, em vez da causa.
→ Isso também resolve o item 11.

**11. `sinceProcessed` é derivado de heurística de amostragem** (`queue-inspector.ts:612`)
Quanto **mais rápido** o consumidor, mais provável o `awaitIdle({sinceProcessed:1})` nunca
satisfazer a condição e girar até o deadline.
→ *Recomendado:* contador monotônico exato de deleções por fila no `SqsEmulator`, exposto via
atributo/endpoint; manter a heurística só no caminho LocalStack.

**12. Não há reset de estado entre testes** (`services/seed-manager.ts:291`)
`seeds.clear` só apaga tabelas que têm arquivo de seed, e faz Scan + BatchDelete item a item.
→ *Recomendado:* `POST /api/engine/reset` que recria o store (trivial agora que existe o store
in-memory). Com `persistence:false` o reset já é "reinicie o processo".

**13. `SelfEngineBackend` não é exportado pelo pacote publicado** (`package.json:12`)
É o padrão dos testes `wire-*` do próprio repo, mas usuários não têm acesso ao modo in-process.
→ *Recomendado:* exportar em `exports` como `./engine` e documentar o padrão.

**14. Zero cobertura e2e do self engine** (`tests/integration/`)
A única suíte de integração é gated em Docker + `LOCALSTACK_AUTH_TOKEN`.
→ *Recomendado:* uma suíte de integração com `engine: 'self'` — não precisa de Docker nem
token, então roda em qualquer CI.

### P2 — qualidade, docs e UI

**15. O gate "100% de cobertura global" exclui `src/server/engine/**` e `src/server/runtime/**`**
(`jest.config.js:9`) — 47 arquivos / ~13 mil linhas, incluindo todo o diferencial do produto.
Os testes existem (45 dos 92 arquivos de teste são do engine), o que falta é a **medição**:
`npm run test:coverage` passa em 100% mesmo com um branch novo de WAL/LRU/FilterCriteria sem
teste. As outras 6 exclusões do arquivo têm comentário explicando o porquê; essas duas são por
omissão.
→ *Recomendado:* adicionar ao `collectCoverageFrom` com exclusões explícitas e comentadas, e um
`coverageThreshold` por path começando no valor medido e subindo.
→ *Alternativa mínima:* corrigir o texto do AGENTS.md §3 para listar o que está fora.

**16. `DELETE /api/services/:name` apaga recursos AWS reais** (`routes/services.ts:181`)
Com 10 tabelas por serviço, remover um serviço pelo dashboard destrói 10 tabelas e os dados

## 5d. Quarta rodada — uma porta só, e o dev local destravado

### O que travava o `npm run dev`

Três coisas, duas delas conflito de porta:

1. **`14566` ocupada pela sua própria instância do host.** O devcontainer usa `--net=host`, então
   compartilha a rede da máquina, e você já roda um LSS lá fora (buckets `s7-*`). O engine morria
   em `address already in use`.
2. **`3101` disputada.** `vite.config.ts` pedia `server.port: 3101` e o `lss.config.json` da raiz
   também dizia `serverPort: 3101`. E o `api.ts` em DEV falava com **3100**, que ninguém escutava.
3. **`3100` nem estava no `forwardPorts`.**

Também achei um bug no caminho: **o CLI ignorava `LSS_ENGINE_PORT`/`LSS_DASHBOARD_PORT`** que o
servidor honra — imprimia `14566` com o engine na `14571`, e como o caminho do PID deriva do
`serverPort`, `start` e `stop` mirariam arquivos diferentes. Corrigido com teste.

### Docker-in-docker: removido

Nada no repo chama Docker desde a v2 — nem o orquestrador, nem o engine, nem os testes. O feature
saiu. `--net=host` você manteve, então o `forwardPorts` continua informativo e a colisão com a sua
instância do host segue valendo enquanto ela estiver de pé.

### Uma porta para tudo (default `14566`)

`serverPort` e `selfEngine.port` **passam a ter o mesmo default**, e serem iguais é o próprio
interruptor: o orquestrador abre **um** listener e decide por requisição quem responde.

`src/server/engine/http/is-aws-request.ts` procura só evidência **positiva** de cliente AWS:
SigV4 no `Authorization`, `X-Amz-Credential` na query, `X-Amz-Target`, qualquer header `x-amz-*`,
caminho do engine (`/_aoss`, `/2015-03-31/`, `/_lss/health`), ou um `POST` `multipart/form-data`
(presigned POST manda a assinatura em campo de form, não em header) / `x-www-form-urlencoded`
(protocolo Query legado). Nada disso → Express (REST API + SPA).

Isso tinha que ficar **na frente** do engine: o dispatcher dele cai em S3 para o que não classifica,
então `GET /assets/app.js` viraria leitura de bucket. E como o teste é por header, **um bucket
chamado `api` não conflita** — o SDK assina, o browser não.

Para voltar a dois listeners: dê valores diferentes às duas chaves.

Provado ponta a ponta com o exemplo inteiro numa porta só: 60 recursos registrados, pipeline
`POST /orders → DynamoDB → SQS → Lambda → S3 + EventBridge → regra → Lambda → DynamoDB`, busca
OpenSearch, presigned POST, dashboard e `GET /api/resources` — tudo no mesmo listener, com
`/assets/*` continuando a servir o SPA e `/api/inexistente` continuando a devolver 404 JSON.

A suíte de integração agora cobre **os dois modos**: `features.test.ts` no listener único (default),
`client.test.ts` com dois listeners.

### Portas depois da mudança

| | antes | agora |
|---|---|---|
| dashboard + REST API | 3100 | **14566** |
| AWS wire | 14566 | **14566** |
| Vite dev (só dev) | 3101 | 3101 |
| exemplo self-hosted | 3140 + 14566 | **14566** |

Nenhuma porta nova: só sumiram a 3100 e a 3140. Os defaults de `LssClient`, do servidor MCP e do

## 6. Respostas diretas às suas perguntas

**"Todas as features estão documentadas?"** Quase. A enumeração está boa — os 47 endpoints,
os 9 emuladores, os 19 tipos CloudFormation e os comandos de CLI estão todos em
`FEATURES.md`/`README.md`, e os testes citados na coluna "Asserted by" existem de fato. As
falhas são de *garantia*, não de inventário: o gate de cobertura não mede o engine (item 15) e
`DELETE /api/services/:name` destrói recursos sem que nenhum doc avise (item 16).

**"Todas as features estão funcionando?"** As que exercitei, sim — pipeline completo, DLQ,
OpenSearch, secrets, presigned POST, persistência, rehydrate. Os bugs reais que achei estavam
em superfícies **de leitura** (explorers) e em **escala**, não no caminho de dados.

**"Quando desligo algo, gera lixo?"** `lambdaRuntime.enabled:false` estava limpo (0 workers,
0 listeners) exceto pelos ESMs (item 5). `persistence:false` gerava lixo e foi corrigido.
`aossSidecar` já era corretamente desligado no modo self. `enableDynamoProxy:false` não abre
nada. O lixo que restava era acumulativo em `~/.lss` — corrigido para escopo por projeto;
sobra apenas o cache legado flat (`~/.lss/orchestrator/cache/<serviço>`) de versões antigas,
que nunca é limpo e é invisível para o código atual.

**"Boa isolação entre ambientes?"** Sim, desde que você use `stateDir` (o que os exemplos
fazem). Sem `stateDir` era compartilhado globalmente — corrigido. O buraco que resta é a
ausência de lock (item 1).

**"Dois processos em paralelo sem bugar?"** Comprovado: duas instâncias completas, quatro
serviços cada, dados totalmente isolados, `stop` de uma não toca na outra. As condições são
portas distintas em tudo (orquestrador, engine, `apiPort`, `invokePort`) e `stateDir` próprio.
O que ainda quebra: modo `artifact` compartilhando diretório de extração (corrigido) e o mesmo
`orchestratorUrl` fixo no `serverless.yml` fazendo dois checkouts registrarem no mesmo
orquestrador (item 20).

**"Dá para usar em testes automatizados?"** Hoje, para uma suíte **serial** contra um stack
fixo, sim — e o `awaitIdle` agora funciona de forma determinística. Para o padrão que você vai
querer (N stacks em paralelo, um por worker do Jest, clean slate por run), faltam os itens 7,
8, 10 e 12. Com `persistence:false` corrigido, o clean slate já é possível hoje reiniciando o
processo.

**"O self host tem sujeira do LocalStack?"** Tinha, bastante — env vars, textos de UI em todas
as telas, endpoint `:4566` exibido como se fosse o endpoint real, campo `localstack` no health.
A maior parte foi corrigida. Sobra o bloco `localstack` fabricado em `/api/config` (item 2), os
textos do CLI e o default `engine: 'localstack'` (item 17). O import estático de
`LocalStackBackend` no `engine-manager` existe, mas o módulo só faz `import` de
`child_process` — custo desprezível; o comentário do arquivo é que exagera a assimetria.

**"É pesado?"** Depois das correções: **128 MB parado com 40 serviços registrados**, +48 MB por
serviço efetivamente invocado, 0,3% de CPU ociosa, boot em 2 s, registro a 22 ms por serviço.
Com `idleTimeoutMs` ligado, o teto fica no número de serviços que você usa ao mesmo tempo, não
no número que você tem.
